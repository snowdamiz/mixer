# Host-only acceptance boundaries

The original stage 4 contract and 32-case matrix remain preserved. The host
binding has no JNI event, probe, or attachment submission API. Its production
files are compiled only with the explicit host bridge module, and its receipts
remain distinct from native Android authority.

For S4-21, actual host evidence can prove fresh attachment/input/probe identities
across fallback, scalar close while no endpoint is present, terminal cleanup, and
the absence of an API that could grant a stale host token authority. It cannot
prove dynamic rejection by JNI event/probe/attachment delivery that does not yet
exist. Record that dynamic subcase as pending for stage 5 and test it against the
real delivery entry points when implemented. Do not add a success-capable host
submission substitute merely to label this case passed. The production lifecycle
requirement remains in scope.

For S4-10, source ordering and concurrent capacity checks do not replace the
required held publication schedule. Observe the actual reserved Swift record
before the corresponding C identity is published, race real admissions, then
resume the original operation unchanged and verify occupancy and final cleanup.

For S4-26, wrong facade, endpoint, lifetime, entry, and native slot generation
require actual rejection at their existing boundaries. Failure-only mutation of
real test-held scalar state may force a rejection, but may never fabricate a
successful native return or cleanup witness. Replay tests may use a genuinely
produced immutable witness; they may not construct or mutate witness fields.

Numeric cleanup serials are minted privately once per facade during final clear,
before lookup is disabled. There is no host caller-supplied serial input or
second final-clear API. Distinguish actual counter-exhaustion and stale immutable
witness replay checks from compile-time constructor privacy and source review of
the final-once rule. Do not describe an unavailable numeric serial-input test as
executed.

Any root acceptance must list its qualified host scope and the remaining dynamic
S4-21 subcase. No full-matrix, native Android, signed-UI, device, published-consumer
or GA pass follows from these scope distinctions. Further implementation may be
assigned through its own reviewed contract; missing native evidence stays open.
