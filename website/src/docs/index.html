01 / YOUR FIRST APP

Start with the source checkout.

Create a project and test your shared Swift code without a cloud account. This quickstart uses the repository CLI for host tests and unsigned iOS Simulator development. The full-platform release examples later in this guide are illustrative workflow references.

1 Get your tools ready

Use macOS 14 or later and Swift 6.2 or later. Install and select Xcode for the optional iOS Simulator steps. Creating a project records your exact Swift compiler and SDK snapshot in mixer.lock; keep that compiler selected while working on the project.

2 Build the CLI from source

Clone Mixer and compile the release executable. The alias below makes mixer available in your current shell.

Terminal · install from source
git clone https://github.com/snowdamiz/mixer.git
cd mixer
swift build --package-path cli -c release
alias mixer="$PWD/cli/.build/release/mixer"

3 Create something of your own

Create the default iOS starter and enter its directory. Your shared Swift feature code and the generated native project live together in MyApp.

Terminal · your first project
mixer create MyApp
cd MyApp
mixer config validate

4 Build and test your shared code

Run the starter’s tests and compile its Swift package on your Mac. These host checks are a useful first loop for models and feature logic.

Terminal · host development
mixer test --platform host
mixer build --platform host

Try the iOS Simulator

With Xcode selected, create an unsigned Simulator build using mixer build --platform ios. Start an iOS Simulator in Xcode, list its identifier, and replace SIMULATOR_UUID below with that simulator’s UUID before running the command.

Terminal · optional iOS Simulator
mixer build --platform ios
xcrun simctl list devices available
mixer run ios --device SIMULATOR_UUID
Doctor is a broader environment inventory.

Run mixer doctor when you want to inspect Swift, Xcode, Java, Gradle, connected physical devices, and matching Android/Wasm Swift SDKs. It returns exit code 2 when any check is incomplete; Android tools and connected phones are not prerequisites for the host steps above. This source CLI’s run command targets an iOS Simulator; its host tests are not iOS or Android device tests.

02 / WRITE WITH MIXERUI

Familiar Swift. A shared foundation.

Put shared screens, state, and application logic in AppFeatures. Use AppModels for your value models and algorithms. MixerUI brings the familiar declarative approach to a UI contract designed for both platforms.

ProjectFeature.swift
import MixerUI

let screen = Navigation("home", title: "MyApp") {
    List("ideas") {
        Section("today", title: "Make something great.") {
            Text("greeting", "Your next idea starts here.")
            Button("add", "Add an idea", action: "idea.add")
        }
    }
}

Stable identifiers give controls and actions a clear identity as your UI changes. Keep the state your screen needs explicit, handle its actions in your feature layer, and use typed native services for platform APIs.

Project areaWhat belongs here
AppFeaturesShared MixerUI screens, feature state, validation, and application logic.
AppModelsShared value models, data transformations, and supported algorithms.
NativeServicesTyped interfaces to services whose implementations run natively.
PlatformsYour iOS and Android entry points, integrations, and native extensions.
mixer.yml / mixer.lockApplication configuration and the pinned dependencies behind your builds.

Bringing an existing Swift app?

Start with a compatibility assessment using mixer import. Move a feature at a time into shared modules while keeping your shipping iOS app. Existing SwiftUI screens may need adaptation to MixerUI; platform-specific screens can stay native alongside shared features.

Terminal · assess an existing project
mixer import /path/to/ExistingApp --output migration-report.json
03 / NATIVE CAPABILITIES

Let each platform be itself.

Mixer compiles Swift for iOS and Android. MixerUI renders supported interfaces through native platform controls, preserving the navigation, accessibility, text behavior, and interactions people expect.

Reach platform APIs through typed services. Your app declares the capabilities it needs, and the native host supplies their implementations. Use native extensions for specialized SDKs, custom views, and the parts of your app that belong to one platform.

SHARE THE FEATURE

One place for the idea.

Share your models, business rules, state, UI structure, and supported asynchronous workflows in Swift.

KEEP THE NATIVE DETAIL

The right tool for the job.

Use native integrations for camera and media, notifications, location, secure storage, purchases, and platform-specific experiences.

A new native capability needs a new store build.

Adding a permission, entitlement, native SDK, native control, or runtime capability changes the installed application. Ship that change through the stores before using it in a compatible update.

04 / KEEP IT YOURS

Your app. Your workflow.

Mixer fits around the tools you already use. Work in your favorite editor, keep your source in your own repository, and connect to the backend that suits your app.

  • Build locally. The Swift SDK and CLI work without a cloud account.
  • Inspect the native projects. Open your iOS and Android projects in Xcode or Android Studio.
  • Own your extensions. Keep platform integrations in designated app-owned files.
  • Keep a way forward. Export your source and pinned SDK to maintain your app in your own environment.
Terminal · export your project
mixer export ../MyApp-export

Hosted builds and delivery are services you can add to this foundation. Your application’s source, data model, and backend remain yours to manage.

05 / DELIVER UPDATES

Keep a good app getting better.

Deliver compatible feature logic and supported UI changes to installed apps. Each candidate is compiled for its target runtime, verified against the installed host’s contracts, and signed before distribution.

  1. 01Prepare & verify

    Compile a candidate and check runtime identity, UI operations, capabilities, and recovery compatibility.

  2. 02Start small

    Publish to a channel and a small cohort. Review release health before expanding.

  3. 03Grow with confidence

    Promote the rollout, halt delivery, or return to a compatible healthy release.

The following commands illustrate the complete release workflow. They are reference examples rather than commands to run with the source-checkout CLI used in the quickstart.

Workflow reference · staged release
mixer update prepare --platform all
mixer update verify <candidate>
mixer update publish <candidate> --channel production --rollout 5
mixer update promote <release> --rollout 25

Replace <candidate> and <release> with the identifiers returned by your workflow. Publishing and promotion are separate actions, so creating a candidate does not expand its audience.

ChangeDelivery path
Feature logicA compatible update, when it stays within the installed runtime and service contracts.
Supported UIA compatible update, when every operation is supported by the installed native host.
Native integrationA store release for new native code, SDKs, permissions, or entitlements.
Runtime changeA store release that includes the new runtime and establishes its compatibility identity.

Recovery is part of the workflow.

Updates activate at a safe cold start. A device retains a healthy implementation, verifies updates before activation, and can recover locally if a candidate fails to start. Offline devices continue using their healthy installed app.

Workflow reference · return to a healthy release
mixer update rollback <release> --reason "validation regression"
Compatibility and release review work together.

Keep persistent data compatible with your recovery targets, test the workflows your change affects, and review applicable store requirements. Update delivery stays within the capabilities and purpose of the installed app.

06 / BUILD & DISTRIBUTE

A clear path to both stores.

Use development profiles while you iterate, then create production builds for distribution. Mixer brings iOS and Android builds, signing, and submission into one workflow with traceable source, artifacts, and logs.

This production sequence is a full-platform workflow reference. For commands supported by the repository CLI, follow the source-checkout quickstart above.

Workflow reference · production distribution
mixer release inspect
mixer build --platform all --profile production
mixer submit --platform all --track testing

Connect your own Apple and Google developer accounts for store distribution. Configure your app identifiers, signing access, environment, and build profile before submitting. Store processing and review remain part of the release lifecycle.

BUILD WHERE YOU WORK

Your local toolchain.

Compile locally, inspect diagnostics, and use your native IDE for platform-specific work.

LET THE CLOUD HELP

Managed builds.

Use isolated macOS and Android runners, secure signing, retained logs, and shared build history.

Follow the release through to availability.

Build completion, upload acceptance, store processing, and readiness for testers are distinct states. Keep an eye on the distribution status until the store makes the build available to your intended audience.

08 / ENTERPRISE

A little room for your requirements.

Bring Mixer into the way your organization already builds and releases software. Enterprise adds identity, infrastructure, and support options for teams with specific operational needs.

  • Single sign-on. Connect your organization’s identity provider and manage access through your team’s policies.
  • Customer-owned keys. Control signing through a managed key service or hardware-backed integration, with access kept separate from build workers.
  • Dedicated runners. Run builds with dedicated capacity and an environment suited to your organization.
  • Audit and release controls. Export audit records, scope service access, and apply production approval policies.
  • Tailored support. Agree on onboarding, migration help, and a support plan for your team.
