# Bounded Swift decode-plan reuse: finite diagnosis

The isolated prototype can avoid repeated count scans while keeping complete build validation and actual-work accounting. It is **not live acceptance**. Root accounting review, independent review, full regression work and any selection into live source remain pending. The cost tradeoff is material. For the finite 96-function/64-resident trace, mostly empty bodies become **2.14% more expensive on a repeated sweep**, 21,594 to 22,056 credits. Each cold sweep adds 1,248 credits. Construction increases from 832 to 4,928 credits, and fixed cache reservations increase from 89,232 to 118,240 bytes. The larger synthetic case, with 512 Nops in most bodies, falls from 262,234 to 166,440 credits on a repeated sweep, a 36.53% reduction. All three sweeps plus construction are 782,814 versus 596,570 credits for that larger case, and 60,894 versus 67,162 for tiny bodies. These are exact charged-work observations, not CPU measurements or a prediction that the full reactor will complete.

The candidate chooses 512 direct-mapped metadata slots per owned cache. This is a bounded private metadata design choice, **not a raised resident, ticket, memory, work or deadline limit**. A cell holds an optional `(absolute function, body offset, body length, type index, Counts)`; it never holds decoded IR, branch resolution, source ownership, a proof or a pin. Its 56-byte measured representation uses 28,672 payload bytes. The mandatory key is checked under the cache's own immutable adopted proof. A different function in the same bucket is a collision and undergoes a full cold scan. The same function with any mismatching offset, length or type fails closed. A hash match never authorizes reuse.

A successful complete `scan_borrowed` is the sole publication source. The full tag, four identity fields and three count fields are published in one infallible assignment after every fallible check and debit. No partial record is observable. A later build or capacity refusal can leave that successful scan metadata retained; sticky first-error semantics prohibit subsequent useful work on the failed runtime. A new cache begins with an empty table, even for byte-identical source. The table cannot be transferred independently, cloned, serialized or installed under a different proof. Wrong runtime/header ownership is rejected before table access or allocation.

Both cold and cached paths keep the signature/policy lookup. Cached counts only size exact allocations. `build_borrowed` still parses the entire immutable body, rejects unsupported/malformed operations, resolves controls, charges byte reads and output writes, and compares actual locals/instruction/target counts before admitting a usable decoded entry. Count corruption remains a build refusal. The original complete validator is unchanged. No syntax-only check or metadata record supplies release authority. Per-cache proof ownership makes a function/offset/length/type key sound here; a shared/global cache would additionally need an immutable module/revision/policy identity and is outside this prototype.

Added work is explicit: one hash credit; one Option-tag probe; one function probe when occupied; three identity probes on a matching function; and three credits for the actual Counts copy on reuse. Cold successful publication debits eight semantic cells plus the three returned count copies before mutation. Each of 512 initialization writes is conservatively charged eight cells, adding 4,096 constructor credits. All existing performed cold scans, build passes, scratch boundaries, allocations, resident operations and cleanup semantics retain their charges. Work, cancellation and deadline checks precede cached copying and publication. No source scan charge is claimed for work that is no longer performed.

The table is a fifth real cache allocation, observable by the allocator. Its payload is grouped into the existing header ticket before allocation, following the already selected resident-index ownership strategy. Its Vec header is part of actual owner sizes. The header stays charged through successful cleanup and every partial-constructor failure until table payload, owner, return and caller storage have ended. No ticket is hidden or added: three existing buffer tickets plus the header still cover five allocated payload vectors. Narrowed category/combined ceilings refuse the table normally.

Header growth is that 312 plus 24 bytes of exclusive owner shape and the 28,672-byte payload. The measured 1,304-byte supplemental PlanInventory is admitted three times. Existing enclosing sizeof formulas propagate foundation and execution owner growth. These are conservative disjoint named-object envelopes; allocator overhead, compiler stack and RSS are not measured.

The original default ceiling remains 16,777,216 cache bytes, 8,388,608 per decoded entry, 64 residents, 64 pins, 86 tickets, 64,000,000 cache-work credits, 268,435,456 combined bytes and the original deadlines. The fixed addition reduces cache space available to residents by 29,008 bytes; it does not expand capacity. Source/metadata/state/execution limits remain unchanged.

This is conservative logical admission arithmetic plus one finite actual construction, not evidence that every category maximum is jointly reachable or that the workload executes successfully.
