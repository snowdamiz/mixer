## Blocking findings

1. **The named transient maps omit actual types and early calculation storage.** `construct_partial` retains a copied `SwiftRunBudget` (136 bytes) and operation capacity getters return that same owned budget shape, absent from construction/operation rows. Standalone release builds and forwards `CacheParts<SwiftMode>` (80 bytes), absent from the permanent cleanup/release map; `PinRecord` (16), actual `FunctionView` (64), and Result wrappers for view/record/release are also absent. The scanner has named `Operation` and `Patch` values (32 each), plus scalar counters and iterator/control-flow objects that are not assigned a typed allowance. Unlike the old frozen scratch, the Swift maps have no documented scalar allowance. Additional conservative copies of different types cannot silently be treated as spare space.

2. **The bound calculation itself happens before its proposed enlargement.** `sum_named` receives literal pair arrays of 304 construction bytes, 368 operation bytes and 432 cleanup bytes, with a 16-byte slice iterator and scalar/Option/closure transfers. `prepare` and `prepare_operation` call the first two before `enlarge_construction_with_wasi`. The maps do not explicitly assign these early objects to any disjoint already-reserved whole foundation slot. A later enlargement cannot justify their earlier existence. A checked scalar fold and explicitly bounded preflight helper with whole-slot phase assignments are reasonable repair directions; candidate 2 must prove the resulting exact call chain.

3. **Several named coverage labels exceed the assertions actually executed.** The opcode test builds many opcodes but checks only locals, branch targets, last End and offset ranges, without comparing each decoded operation to independent owned IR. The pin test has 64 recursive live pins and 64 sequential distinct residents, not 64 simultaneous distinct pins followed by a rejected 65th. The parameters test omits 129-parameter rejection. The ownership label mentions owner-identity exhaustion but only nonce exhaustion has a seed. The sticky test exercises PinLimit only, rather than every terminal kind. The layout snapshot named test prints layouts; its legacy parity evidence is in the separately bound replay, not in that body. Existing separately executed descriptor and foundation tests do cover many other descriptor/narrowing/owner assertions. The final coverage map must distinguish such evidence, supplementary review probes, and genuinely missing cases.

No behavioral under-reservation exploit is claimed from these omissions: this is a failure to establish the required exhaustive logical named-object bound. Root authorized a separately preserved candidate 2 repair after these findings. Candidate 1 remains immutable review evidence.

## Ownership, failure order and final tail audit

The cache moves the whole existing `AdoptedProof`, retaining both original proof tickets. Header arithmetic excludes only the already-accounted 664-byte proof header: the remaining 328 bytes include the two adopted ticket handles (48), three vector handles (72), four optional cache ticket handles (96), copied cache usage (96) and owner/nonce (16). Source/metadata remain solely in their retained categories. The fixed payload is 8,704 slots + 1,024 pins + 16,384 patches = 26,112 requested bytes, giving 63,200 cache bytes including the candidate 1 header. There is one permanent 512-Patch buffer and no per-miss patch allocation. Entry bytes remain one aggregate ticket; the slot capacity and victim drop before build keep resident-or-incoming entries at 64. Pins do not create payload tickets.

Pairing preflight precedes owner take/drop or work, including both adopted tickets and the intact cache header. A rejected release returns the original owned pin; existing tests and the additional simultaneous-pin test show terminal release remains admission/work independent. Pin acquisition rolls back the live pin on scan/build/publication failure; aggregate entry/live admission rolls back on payload failure. Existing prefix/cancellation ordinal enumerations run through reset, scan, build, planning and publication. Victim planning has no effects until its full precharge/check succeeds. Failure after committed victim drop may leave those victims gone, matching the frozen route's order.

At cleanup, actual entry vectors are passed by value into `drop_reserved_with_wasi` and dropped before refund. All entries, fixed vectors and the whole adopted proof continue draining despite a later invariant. Rejected initial pairing leaves the exact owner Some; destructive entry leaves None and returns the same header ticket in a tail. Omitted completion retains its charge. `drop_cleanup_return_storage` consumes the original 1,136-byte tail and actual caller storage, drops its failure/storage, and **returns before** the refund starts. Only `CleanupCompletionParts` (40 bytes: two borrowed handles and the same optional ticket) survives. The published map assigns that small tuple to an entire phase-alternative control transfer slot, not to padding inside a live control; ordinary phases must already have completed. The helper boundary is structurally valid in candidate 1, independent of the other missing component map rows.

After that boundary, the existing 16,504-byte foundation classes can cover the reviewed selected caller protocol: control owner in slot1, small completion tuple in whole control-transfer slot2, eventual control consumption in slot3 after the exclusive borrow ends; four copied failure/Option/Result shapes, four standalone usage shapes, six ticket shapes, and six optional WASI observations. The longest refund fault path is drop_reserved/refund/cleanup_fault/fail/usage (five observed parameters), plus the retained caller observation. Refund Result ends at its statement before record_cleanup. The tail's prior failure has already been dropped; its immutable first cause remains in the actual control. Large owner/Result/Option values must be consumed into the helper before header refund. Arbitrary generic caller storage and a later composed executor are **not** proved by this selected private test-caller map.

## Validation deadline repair

The reviewed test-only file hash is `5fc2aafcd477f3f9845e787116a4ab73ec68319c0aa1996090a57b95571a3cb6`. `deadline_at` clears its marker for each attempt, sets it only at the selected actual allocation request, requires Deadline and zero leak/reallocation for every attempt, and accepts only `reached && CALLS == ordinal`. Early expiry requires CALLS < ordinal and cannot count as coverage. Exhausted bounded retries return Err. Deterministic `[0,...]` retry and `[0,0]` exhaustion run inside the same observer ownership lane. No success, wrong failure kind, leak, skipped ordinal or extra cleanup allocation can be converted into coverage by retry. This is sound for the stated synchronous synthetic allocation boundary; it does not validate device/compiler/full-target timing.
