# Hosted identity and authorization contract

Status: candidate for root contract freeze; implementation and hosted qualification remain pending. This is a bounded W11/W16 seam for product-plan §§6.4, 13.1–13.5, 17 and 18.1. It does not reduce the remaining product scope or verify a GA gate.

The implementation target is the selected Phoenix/Plug/Bandit API with Ecto/Postgrex on PostgreSQL, later qualified on Neon. Root owns the new **`hosted/`** foundation, OTP application `:mixer_hosted`, modules `MixerHosted`/`MixerHostedWeb`, initially exposing liveness only. The next identity lane extends that exact application after root freezes ownership; it does not create a competing application. The Go service remains the local wire, storage and rejection-behavior reference; this proposal does not turn it into a production identity backend. Identity/SSO provider, Elixir authentication libraries, deployments and real credentials are deliberately unselected.

## Trust chain and public interfaces

The closed chain is:

`HTTP credential → configured issuer verifier → verified identity → authoritative principal + credential state → current tenant membership/policy → transaction-bound authorized target/action → domain mutation + audit + job intent`

Each step has one owner. Token claims, request JSON, URL segments, query parameters, edge headers and console state cannot supply authoritative membership, product roles, actor IDs or release rights. A cryptographically valid token is identity evidence, not project permission. OAuth scope can narrow the resulting permission; it cannot create membership.

Implement these internal modules first; `conn.assigns` is transport, not an authority constructor:

| Module/seam | Contract |
| --- | --- |
| `MixerHosted.Identity.Verifier` behavior | `authenticate(bearer, now)` returns a verified identity or `unauthenticated`/`identity_unavailable`. Verified result contains exact configured issuer ID/version, subject, registered client, validated credential reference/issued-at/expiry, and the issuer-profile identity class. It contains no project, organization, product role or permission grant. Only the verifier adapter constructs it. |
| `MixerHosted.Authorization.with_authorized_transaction(identity, request, callback)` | Starts the Repo transaction, resolves current principal/credential state, validates target existence and authoritative policy, then invokes `callback` with an internal transaction-bound context. Never returns a reusable authorization ticket. The context carries principal ID/kind, credential reference, target, action, policy revisions and immutable audit actor. Context cannot be accepted on another Repo connection, request, action or after commit/rollback. |
| `MixerHosted.Release.Repository` | Operations accept that context and use its connection. They reassert exact row target/action; no public `role` argument or caller-constructed access struct. Reads and writes use the same membership-aware RLS policy. A module-private constructor is an API discipline, not an Elixir sandbox against malicious code inside the trusted BEAM process. |
| `MixerHosted.Release.Command` | Parses a closed action (`artifact.read/upload`, `release.validate/publish/promote/rollback/halt`, `audit.read`, later explicit actions). Loads referenced immutable resource under tenant scope when necessary and derives app/environment/platform/runtime from it. It cannot use a client-supplied environment to authorize a different stored resource. |
| `MixerHosted.Audit` | Builds actor and authorization evidence from the internal context. Caller reason is bounded descriptive text only. Writes actor, domain changes, policy/approval references, idempotency result and Oban intent atomically. |
| `MixerHosted.Delivery` | Separate public read interface, with no `VerifiedIdentity` dependency and no private-data repository access. Its authority is already-published, signed data. |

Do not expose `authenticate(..., org, project, role)` as a hosted contract. It conflates identity with policy. Do not implement a fallback from failed hosted verification to local configured tokens.

The first adapter maps only the exact configured OAuth scope names `mixer.artifact.read`, `mixer.artifact.upload` and `mixer.audit.read` to the three supported actions. An absent corresponding scope denies that action even when membership permits it. Additional unknown scopes contribute no permission. No token scope such as `owner` or `project:*` creates a membership or wildcard grant.

## User, service and CI identity

Human login uses an external OIDC provider through an authorization-code flow with PKCE and standard redirect/state/nonce validation. Identify a human by the exact issuer and subject binding, then an internal non-recycled principal ID. Email/name/domain are display or invitation information, never identity linkage or membership proof. Pairwise subjects and API access-token subjects may differ: the selected provider adapter must establish a documented stable binding, not equate users by email. The API accepts an OAuth access token intended for the API; an OIDC ID token is not accepted as a resource credential. The identity/ID-token distinction and issuer/subject semantics follow [OIDC Core §§2, 3.1, 5.7, 8](https://openid.net/specs/openid-connect-core-1_0.html); redirect and PKCE requirements follow [OAuth Security BCP §2.1](https://www.rfc-editor.org/rfc/rfc9700.html#section-2.1). Full browser/CLI login and session UI are later W14/W13 work, not supplied by the first slice.

For the first verifier adapter, select the standard JWT access-token profile in [RFC 9068 §§2–4](https://www.rfc-editor.org/rfc/rfc9068.html#section-2): verify signature, exact issuer, API audience, token type, time claims and required identity/client/token identifiers with an established JOSE library. Keep ID-token, API-token and workload-token validation rules distinct. Fix the permitted asymmetric algorithm set in reviewed issuer configuration; reject `none`, algorithm/key confusion, unsupported critical headers, malformed/duplicate JSON claims and ambiguous key selection. `kid` is a bounded lookup key, not a path or SQL fragment. Never fetch a URL supplied in `jku/x5u` or claims. These validation principles follow [JWT BCP §§3.1, 3.8–3.12](https://www.rfc-editor.org/rfc/rfc8725.html#section-3). This is a selected compatibility profile, not a claim that every OIDC provider emits it; a provider requiring a different profile needs a separately reviewed adapter and tests.

Service accounts are internal `kind=service` principals owned by one organization, with explicit project/action/environment grants. Their credentials use a registered confidential OAuth client; client-credentials grants are service identity, not an absent human masquerading as a user. [RFC 6749 §4.4](https://www.rfc-editor.org/rfc/rfc6749.html#section-4.4) defines that grant. Production must qualify asymmetric client authentication or a provider-supported workload federation path; never distribute a long-lived owner bearer token to build jobs. Service accounts cannot own/transfer organizations, administer membership, manage billing or count as a human second approver. Creator/remover names are management history; grants do not inherit the creator's current role implicitly.

CI first obtains a short-lived workload assertion from its configured CI issuer, then an API-audience access token from the selected authorization server. The CI binding records an exact reviewed workload tuple (issuer, subject/client, repository identity, protected ref/environment and allowed workflow as supported by that issuer), service principal, target limits and credential ceiling. A repository or branch name received in request JSON/header is not evidence. Raw workload assertions with the wrong audience/type are rejected by the API. If using token exchange, use provider-supported [RFC 8693](https://www.rfc-editor.org/rfc/rfc8693.html); this contract does not introduce a bespoke token format or Mixer token broker. Do not silently drop unavailable protected-ref/workflow guarantees. Until the provider's issuance and claim semantics are qualified, CI federation remains pending.

Identity class is selected by the registered issuer/client profile and authoritative identity binding, never by a token's arbitrary `kind`, `roles`, `groups`, `organization` or `project` claim. Unknown identity bindings do not auto-create membership. An explicit invitation acceptance or organization bootstrap transaction creates membership; domain matching alone grants nothing. Tenant SSO/SCIM lifecycle and linking multiple login identities require later audited workflows.

## Product role and environment policy

Use the six role names from §17, stored canonically as `owner`, `administrator`, `developer`, `release_manager`, `billing_manager`, `viewer`. These are product roles; PostgreSQL login roles and old `reader/editor/publisher` remain separate concepts.

The following is the proposed baseline ceiling for root freeze. A role lists eligible capabilities, not unconditional access to all projects/environments. Membership must be active and assigned to the target project (or an explicit organization-wide project binding). Any deny, environment restriction, authentication requirement or service ceiling still applies. Multiple eligible memberships may contribute capabilities, followed by all applicable restrictions; absence or unknown policy fails closed.

| Product role | Project/resource capabilities | Organization/commercial capabilities | Release eligibility before explicit environment grant |
| --- | --- | --- | --- |
| owner | Project create/manage, metadata, artifacts, validation, audit | Membership/service management, billing, ownership transfer under its own protected policy | Eligible in development, staging, production; no environment-policy bypass |
| administrator | Project create/manage, metadata, artifacts, validation, audit | Membership/service management except owner grant/removal/transfer; billing summary only | Eligible in all environments; no environment-policy bypass |
| developer | Assigned-project metadata/artifacts, upload, validate, build request, audit | Own profile only | Eligible for explicit development/staging grants; production release requires a release-manager/owner/administrator membership |
| release manager | Assigned-project metadata/artifact read, validate, audit | Own profile only | Eligible in explicitly granted environments; artifact upload/build request requires an additional eligible role |
| billing manager | Organization billing/usage records required for commercial work; no private artifact/source/log permission | Billing, invoices, spending caps | None |
| viewer | Assigned-project metadata, artifact read and audit read | Own profile only | None |

Source archives, logs, symbols, source maps, credential material and support impersonation each need a separately named permission; `metadata.read` does not expose them. They are denied until implemented. The first slice supports artifact read/upload and audit read only; table entries do not promise unimplemented endpoints.

Environment records are distinct rows identified under `(organization, project, application, environment)`. Development/staging/production labels classify risk; environment IDs alone do not grant anything. Release grants bind principal/membership, project, app, environment, action set, optional channel/runtime restrictions, expiry and revision. No implicit `*` interpretation; organization-wide bindings and wildcards require explicit stored policy and expansion limits. `publish`, `promote`, `rollback` and `halt` are separately checked. Granting publish never implies rollback or production promotion. Promotion authorizes both source inspection and the destination binding and preserves signed manifest immutability.

Service grant permissions intersect the service principal's project/action/environment ceiling, active credential/CI binding and token scopes. They never become an `owner` role. Human role capabilities intersect explicit environment release grants and token scopes. An owner/admin can manage policy through an audited operation, but cannot bypass a policy on the release command that is already in progress.

Optional two-person production policy is server state: an immutable proposal digest binds exact artifact, source revision, runtime cohort, destination scope, action, rollout parameters and policy version. Approval is an independent active human principal with the required current permission; the actor cannot approve their own proposal or satisfy both slots with two sessions/accounts linked to the same principal. Changed proposal, revoked approver, expired approval or changed policy invalidates it. When customer policy does not require second approval, do not insert one. An already-authorized CI flow can execute with stored policy/approval evidence. This first slice implements no release/approval operation and cannot accept a production release.

## Authoritative persistence and RLS

Create coordinated new hosted migrations under `hosted/priv/repo/migrations/`; do not change the historical Go `001_release.sql` checksum or make Go accept an unknown schema version. Use separate migration-owner and runtime credentials. Preserve FORCE RLS, least-privilege startup checks, transaction-local tenant settings, canonical wire checks, immutable records and monotonic assignment sequences in the hosted translation.

Minimum hosted records, with foreign keys and explicit state/expiry constraints:

| Record | Required meaning and mutation authority |
| --- | --- |
| `identity_trust_profiles` | Operator-controlled issuer/audience/client/class/JWKS/algorithm profile and active/version state. Tenant administrators cannot edit global trust or claim-to-identity semantics. Deploy-time configuration is copied and validated before use; a reload atomically replaces a complete version, never mutates shared maps in place. |
| `principals` | Non-recycled opaque ID, human/service kind, active/disabled state, `valid_after`, revision. Service principal also has owning organization. No hard delete that removes audit meaning. |
| `external_identity_bindings` | Unique exact `(trust_profile_id, issuer, subject, registered_client)` to principal and class; provider-specific stable-user mapping is explicit. Immutable binding changes require controlled linking/migration, never an email join. |
| `credential_state` | Issuer/client/principal credential-family or session reference, validity/revocation state and revision, plus token-identifier denials where needed. Store bounded references/digests, not raw bearer/refresh tokens. A verified token's `jti` is evidence to look up, not an ID chosen by a request body. Denial retention is bounded by the maximum remaining token lifetime plus skew. |
| `organizations`, `projects`, `applications`, `environments` | Existence, parent foreign keys, active/deleted state and environment policy class. Do not infer membership from existence of an app ID. Source/destination environment belongs to the exact application/project. |
| `organization_memberships`, `project_memberships` | Principal, role, explicit scope/binding, active/revoked state, optional `not_before/expires_at`, revision, grantor audit ID. Exactly one non-recycled membership identity per grant lifecycle; invitation is not active membership. |
| `environment_release_grants`, `service_grants`, `ci_bindings` | Server-owned action/target ceilings and expiry, with granting policy and revision. An API credential never carries the authoritative copy. |
| `authorization_heads` | Organization and project policy revision/lock rows. Every policy-affecting write, including membership/role/grant removal, locks and increments the relevant head. Principal/credential state has equivalent lock/revision discipline. |
| `audit_events`, `idempotency` | New hosted versioned audit actor/evidence and principal-bound dedup, described below. Append-only audit constraints and transactional domain/event/job behavior remain. |

The first slice needs trust configuration plus principal/binding/credential state, organization/project/app/environment existence, memberships, authorization heads, and artifact/audit/idempotency tables. It should create only the supported action policies; release/service/CI/approval tables and endpoints can follow as separate migrations. Its schema must reject unsupported release actions. Membership provisioning for tests is an explicit migration-owner fixture; no runtime bootstrap endpoint that makes the first caller an owner.

Hosted runtime cannot grant itself membership by writing these tables. For the first slice its role has only scoped read access to identity/policy records and domain operations. A later member-management writer uses narrowly reviewed database functions/privileges with actor checks and the same lock protocol; do not grant blanket authz-table DML to the release API because future member endpoints may need writes. Never use a migration-owner pool in API/Oban processes. Membership policies must avoid recursive RLS; a narrowly scoped resolver/policy function with fixed `search_path`, no dynamic SQL, least-privileged owner and no PUBLIC execution is an acceptable candidate only after real PostgreSQL adversarial review.

`mixer.role` alone cannot authorize the hosted store. Hosted transaction-local context includes principal/credential reference, exact organization/project, action and derived resource target. Policies join authoritative current membership/credential state and inspect the actual artifact/assignment target; there is no `is_admin=true` or token-role bypass. Add normalized app/environment/platform/runtime columns with checks tying them to the canonical signed scope before using them in policies. Private reads require project visibility and the relevant action; published delivery uses a distinct role/policy and cannot read identity, membership, audit, outbox or private object tables. Identity/policy rows also require appropriate RLS/grants; no global member-list leak.

Settings are parameterized `set_config(..., true)` inside the actual Repo transaction, on the same connection as the query. Never use session `SET` on pooled connections, detached async tasks, or a separate Repo checkout. Clear/missing/unknown context denies. Connection reuse, rollback and failed authorization must be tested for context leakage.

Resource resolution is not an authorization shortcut: the request initially contains route tenant + action + immutable resource reference. Inside the locked transaction, a narrow resolver may read only the stored canonical target metadata under membership-aware tenant visibility. It does not return payload/log contents to the caller. Then resolve the complete target and re-evaluate action/environment policy before giving the repository its context. Upload target comes from the validated immutable manifest bytes. Project audit requests use an explicit project-only target/action; they cannot be reused for an artifact. Policies evaluate actual row scope, so lookup does not depend on an untrusted guessed environment GUC.

RLS is defense against omitted predicates and application routing mistakes. A database role permitted to set identity GUCs can impersonate a principal if the trusted application/DB credentials are compromised; a plain GUC is not cryptographic identity proof. Do not claim this design defeats SQL injection or a compromised API process. Limit arbitrary SQL, use parameterized queries and isolated roles, deny unsafe ownership/role chains, and test policy/grant boundaries. Owner/superuser/bypass behavior and policy race considerations follow the [PostgreSQL row-security documentation](https://www.postgresql.org/docs/current/ddl-rowsecurity.html). A stronger hostile-API threat model would need a separately authenticated DB/session authority design; it is an explicit security review question, not a hidden guarantee here.

## Transaction, revocation and durable work semantics

1. Verify cryptographic identity before opening a database transaction or parsing a large private body. Parse bounded command metadata; perform expensive signature/content checks outside the policy lock, then re-bind exact immutable bytes/target inside the transaction.
2. Within the transaction, resolve principal and credential state. In canonical order acquire shared locks on trust-profile state, principal state, credential-family state, organization authorization head, then project authorization head. Evaluate validity and current membership/grants using fresh queries after these locks at READ COMMITTED isolation. Authorization writers acquire conflicting update locks on affected state/heads in the same order before modifying policy; bulk IDs within one class sort consistently. A token denial insertion locks the existing principal/family row too, so a missing denial row is not an unlocked revocation race. Every admitted credential resolves to existing active state; unknown references deny. Concurrent membership provisioning needs the head row too, so absence is not cached or bypassed. This protocol applies to reads as well as writes.
3. Acquire the existing per-tenant mutation/sequence lock for mutation. Bind action, organization/project and actual stored/signed resource app/environment/platform/runtime. Recheck role eligibility, explicit grants, scopes and approvals as relevant. A revoked credential cannot retrieve a cached successful idempotency result.
4. Execute domain change, immutable actor/audit, idempotency result and Oban intent in the same Repo transaction. [Ecto.Multi](https://hexdocs.pm/ecto/Ecto.Multi.html) supplies transaction grouping; it does not create authorization or guarantee a later external effect exactly once. No network request, provider callback, customer code or signer call runs while holding authorization locks.
5. Release the locks at commit/rollback. A revocation transaction waits for admitted requests holding the old shared lock. Once revocation returns success, a newly admitted protected transaction cannot use the revoked state. An already-admitted operation may have committed before revocation returned; revocation is not time travel. Record both ordering and bounded lock/statement timeouts in tests.

Fresh principal/credential/membership checks occur for every protected request; no positive authorization cache in the first slice. JWT expiry limits credential admission, while database revocation independently blocks requests before expiry. Proposed maximum token lifetime: human API access token 15 minutes, service/CI token 5 minutes; allowed future `iat/nbf` clock skew at most 30 seconds, no acceptance at/after `exp`. Reject impossible orderings and excessive lifetimes. Bounds are Mixer policy, not OAuth defaults. Use a monitored authoritative clock; uncertainty beyond the budget fails protected operations closed. Check time at transaction admission and immediately before persisting an effect; transaction duration is bounded to 5 seconds. A request admitted while valid can finish within that bounded transaction, so do not promise that a transaction can never commit just after the token's wall-clock expiry.

Disable principal, revoke credential/family, remove membership, revoke environment grant and disable issuer/profile are distinct operations with durable revisions/audit. The first slice checks all applicable active state and `valid_after`; a global incident response must be able to disable a trust profile without waiting for JWKS cache expiry. No provider logout webhook is assumed to prove revocation; SSO session logout/revocation synchronization needs a qualified provider adapter. Denials are local authoritative state and survive API restart.

An accepted asynchronous command is a durable intent; its originating bearer token is never stored in an Oban argument or sent to a worker. Credential expiry alone does not retroactively cancel an accepted intent. Before any privileged dispatch/sign/publish, re-evaluate principal state, explicit credential revocation, current membership/environment policy and approval against the immutable intent. Revocation can cancel undispatched intents; an external effect already completed requires an explicit halt/rollback/reconciliation workflow. Cleaning up an expired token-denial entry must not erase pending-work revocation: atomically cancel affected undispatched intents or retain a credential-revocation tombstone until those intents are terminal. Worker identity is a separate least-privilege service principal; original actor and worker executor are both retained. Delayed execution is not authorized merely by an old role claim or an old `AuthorizedContext`. This dispatch seam is a later slice; no hosted outbox dispatcher is delivered here.

## Audit actor and idempotency

New hosted audit schema carries an immutable actor snapshot: internal principal ID and kind, exact identity-binding/profile ID and version, stable issuer/subject reference, registered client, credential reference, authentication/decision time, membership and policy revisions, exact target/action, approval/intent ID where present, and executor identity for background effects. Do not store raw JWT, refresh token, secret, full claims, email-as-identity, form values or unrestricted job metadata. Display names are optional redacted snapshots, not the actor key. Later rename/removal cannot rewrite history. Audit retention/privacy rules still need product implementation.

The server generates request/correlation IDs, trusts source IP only through an explicitly configured Cloudflare/ingress chain, bounds reason to 512 bytes, and does not accept `X-Actor`, arbitrary `X-Forwarded-For` or JSON actor fields as authority. Reasons explain intent and never grant it. Audit construction happens inside the same transaction as the domain write. Rejection logs are sanitized, bounded security observations separate from the immutable successful-domain event chain; failed auth cannot manufacture a successful domain event or unbounded high-cardinality labels.

Keep tenant/key uniqueness for idempotency and bind a new row to the immutable principal ID, canonical action/target and request hash. Same principal with a refreshed eligible credential can retry. A different principal using that key receives `409 idempotency_conflict`, with no cached body disclosure. Re-authorize current policy before reading the cached success; revoked membership never becomes valid because a response exists. Retain the original audit actor/event on a retry rather than producing a new apparent publisher. Historical Go rows without principal binding remain historical/local; do not silently assign them to the currently authenticated user or change their event hashes.

## Errors, resource limits and outages

Keep the existing versioned JSON envelope shape (`error.code`, `error.message`, `request_id`), bounded bodies and no-store private responses. New hosted codes and HTTP behavior are explicit:

| Condition | Result |
| --- | --- |
| Missing bearer, invalid signature, unconfigured issuer/client/type, expired/revoked token/principal, unknown identity binding | `401 unauthenticated`; standard Bearer challenge, no token/subject/role diagnostics. Missing credential has no error detail in the challenge. |
| Duplicate/ambiguous authentication mechanisms or malformed authorization syntax | `400 invalid_request`; reject rather than choosing one credential. |
| Valid identity without visible target organization/project | `404 not_found`, indistinguishable from a nonexistent tenant/project. Do not expose member lists. |
| Visible project but insufficient supported action/environment permission, approval or assurance | `403 permission_denied`; no secret policy contents or resource names. A nonvisible resource remains `404`. |
| Policy/principal DB unavailable, expired trust-key cache with refresh failure, configured issuer temporarily unreachable when a refresh is required | `503 identity_unavailable` or `503 authorization_unavailable`, with request ID and bounded retry advice. Never downgrade to anonymous, development credentials, a stale allow decision or a failed-open release. |
| Authoritative fresh JWKS has no matching key / bad signature with a known key | `401 unauthenticated`; never retry the signature with an unrelated key or algorithm. |
| Auth concurrency/rate/refresh capacity exceeded | `429 rate_limit` with bounded `Retry-After`; do not start unbounded verification tasks. |
| Idempotency mismatch, changed proposal or stale assignment sequence | Existing `409` conflict semantics; no second side effect. |
| Commit uncertain | `503 storage_unavailable`; retry same idempotency key after fresh identity/policy checks. |

Bearer header/challenge and invalid-request/invalid-token behavior follow [RFC 6750 §§2–3](https://www.rfc-editor.org/rfc/rfc6750.html#section-2); the non-enumerating tenant/resource status and service-specific codes above are Mixer policy. API error responses redact network URLs, DSNs, credentials, claims, SQL and provider response bodies. Preserve internal cause codes only in sanitized operator logs.

Initial resource bounds, to pin and test before implementing the verifier adapter:

| Boundary | Proposed bound / behavior |
| --- | --- |
| HTTP credential | One `Authorization: Bearer` value; at most 4096 bytes as in the Go reference. No URL-query/body token; no automatic cookie-to-bearer conversion. Cookie-based console sessions need a later explicit CSRF/origin/session contract. |
| Trust inventory | At most 8 configured active issuer profiles, 16 verification keys/profile, 128-byte `kid`; oversized or duplicate/ambiguous key sets reject atomically. The issuer is an exact configured string; it never initiates discovery for an attacker-provided issuer. |
| Metadata/JWKS network | Preconfigured HTTPS endpoints with ordinary TLS chain/hostname verification, allowlisted origin/path, no redirects, cookies, auth forwarding or token-selected URLs. Reject private/loopback/link-local destinations in hosted mode, including DNS rebinding; an explicit isolated loopback test configuration is test-only. Max 256 KiB response, 2-second total fetch deadline, 4 concurrent fetches/process. Endpoint/issuer consistency follows [RFC 8414 §3.3](https://www.rfc-editor.org/rfc/rfc8414.html#section-3.3). |
| Key cache | Atomic validated profile/key snapshots; effective lifetime is no greater than HTTP freshness or 300 seconds, never indefinitely extended by failures. No stale-key use after the bound. Known key with fresh cache needs no provider request. Per-profile single-flight refresh, at most once/30 seconds; unknown-key negative cache at most 128 entries/profile for 30 seconds, with deterministic eviction. Cold start must obtain an authenticated valid key set or protected endpoints remain unavailable. |
| Key rotation | Publish overlapping old/new keys before issuance switches and retain old keys through the intended token validity window plus skew; test actual provider behavior. On successful refresh removed keys stop validating. Emergency profile disable/revision is checked with protected requests, independent of cache freshness. Algorithm/trust changes need validated version replacement and audit. |
| Policy/DB | No membership/permission allow cache. Fixed query/pool/concurrency budgets, 5-second transaction/statement bound, shorter lock timeout; errors roll back and deny. No tenant-controlled SQL identifiers or unbounded membership scans. Bound memberships/grants per request using indexed exact target lookup; capacity configuration/overflow returns unavailable, not an approximate allow. |
| Request pressure | Retain bounded global admission and IP limits, add issuer/credential/principal limits only after trusted identity, and bound their cache entry count. Do not let random bearer strings or `kid` values allocate an unbounded map or turn every request into an external fetch. Exact protected-request capacity is measured in the first slice, not inferred from the Go limit of 128. |

Identity-provider outage can leave already-issued, unexpired tokens usable while verified keys are fresh and the local principal/policy database is healthy. New login/refresh may fail. Once required keys are unavailable/stale, protected operations fail closed. Membership/DB outage fails protected operations even with a valid signature. The dedicated public update path continues using published signed assignments/artifacts without a live identity or membership call; it still applies its existing narrow scope, cache freshness, signature and replay rules. Identity failure must not brick an installed app or expose a private object.

## What changes first, and what stays

| Current reference | First hosted change / invariant |
| --- | --- |
| `Config.Tokens`, `Token`, `auth` | Keep Go local-only as-is. In Phoenix introduce explicit verifier trust configuration and verified identity interface. No hosted public role/tenant/actor configuration disguised as OIDC claims. Snapshot and validate trust configuration before retaining it; keep config-ownership regression. |
| `route` method-based `reader/editor/publisher` selection | Translate to a closed action registry with exact route/method/body shape. Derive full target after bounded parsing/immutable record lookup. Unknown routes/methods/actions fail closed; `GET channels` must not accidentally imply publish. |
| `access{tenant, Actor, Role}`, `access.require` | Replace in the hosted repository with transaction-bound authorization context. The six human roles are evaluated from DB records; resource environment rights are enforced after target resolution. No new production Go access type is required. |
| `releaseStorage.transaction(ctx, access, role, key, hash, event, callback)` and private `artifact/history` | Hosted equivalent owns both authorization and domain transaction; caller cannot select role or audit actor. Add principal-bound dedup and auditable authorization revisions. Split audit access from future internal job status/lease visibility instead of exposing Oban internals as a generic reader right. |
| `postgresStore.begin(ctx, tenant, role)`, RLS functions/policies | Hosted migration introduces identity/membership schema and context/policy-aware RLS, exact app/environment columns, row lock protocol and least-privileged runtime checks. `mixer.role=publisher` alone never grants hosted publication. Preserve transaction-local context and startup rejection of owner/elevated/unknown-schema roles. |
| `Event`, audit verification/hash encoding, `Dedup`, SQL `audit_events/idempotency` | Introduce an explicit hosted event schema version and immutable actor/policy fields, principal binding for new dedup. Preserve old event bytes and wire fixture interpretation; parity/migration requires separate evidence. |
| Signed manifests, assignments, canonical protocol v1/v2/v3, artifact hashes, compatibility, monotonic sequence | Remain their own frozen contracts. Authentication does not loosen signing/compatibility checks or grant signing keys to the API, CI or worker. First hosted slice implements v3 only and rejects unsupported versions; later parity qualification covers the complete supported matrix. |
| `publicArtifact`, `publicChannel`, `update` | Remain public published-only interfaces; public organization/project/app IDs are selectors, never admin credentials. No memberships or private object paths in the mobile client. Separate delivery DB/access role in hosted design. |
| Local filesystem store, Go migration 001 and local fixtures | Remain local reference evidence. No attempt to add hosted memberships or production dispatch to them. |
| Production readiness `ValidateConfig`/health response | Go remains production-disabled. An identity slice cannot remove the guard or claim Cloudflare/Neon, external delivery, job dispatch, signing, isolation or operational readiness. |

## First executable vertical slice and ownership

Freeze this contract before dependent work. Root's active foundation lane owns `hosted/` application/config/Repo/Oban/liveness files and initial lockfiles/migrations. After that slice freezes, assign one bounded **identity + membership lane** to `hosted/lib/mixer_hosted/identity/`, `hosted/lib/mixer_hosted/authorization/`, `hosted/lib/mixer_hosted/release/`, their focused tests and `verification/hosted-identity-v1/`. Root explicitly coordinates shared router/config/dependency and migration edits before that lane starts. Assign an independent reviewer separately after the candidate source tree is frozen. Coordinate root-owned `THIRD_PARTY.yml`, trackers and product plan; do not let parallel agents edit common migration or trust schemas. A separate later CI/provider lane can depend on the frozen verifier behavior and schema; it must not redefine principal/role meanings.

The first end-to-end development slice is **real signed API token → authoritative membership → private v3 artifact upload/read → immutable actor audit + principal-bound idempotency**, entirely headless and local, without a public production route:

1. Reuse root's pinned Phoenix/Plug/Bandit/Ecto/Postgrex application under `hosted/`; add a maintained standard JOSE/OIDC verifier dependency only through coordinated lockfile/inventory edits. Compile the application and retain its API/processor separation; do not duplicate business behavior in edge code.
2. Implement one fixed issuer-profile adapter for RFC 9068 access tokens with synthetic test keys and a bounded loopback JWKS server in the integration harness. This is cryptographic protocol testing against a controlled issuer, explicitly not a real external provider/SSO receipt. No real credentials or cloud resources are required.
3. Implement the minimum records and membership-aware FORCE RLS described above in a disposable real PostgreSQL instance with owner/runtime separation. Provision two organizations/projects and all six human roles plus a disabled principal using owner-controlled test fixtures. Implement principal disable, credential denial and membership revoke through a test-only owner harness to exercise the real lock protocol; no unaudited production admin endpoint.
4. Expose only the authenticated private v3 `PUT/GET artifacts/:digest` and `GET audit` subset, retaining exact wire/signature/host compatibility and immutable content checks. Upload requires an active eligible membership and `artifact.upload` scope; read/audit require their own action scopes. Bind manifest app/environment before writing. No `publish/promote/rollback/halt`, login UI, service federation, signer, production build execution or external dispatcher in this slice; unsupported endpoints reject.
5. In one Ecto transaction store immutable artifact metadata/content reference, successful actor audit and principal-bound idempotency. If enqueue is included, insert a nondispatching Oban job in the same transaction and label it as local no-external-effect evidence. A fake queue is not Oban integration; Omitting jobs leaves the transactional job gate pending. R2 blob integration/migration is separate: use a clearly labeled disposable local blob fixture and never claim it proves R2 isolation or durable remote upload.
6. Run the matrix below through actual HTTP + real cryptographic verification + real PostgreSQL, with source digests/versions/output and observed cleanup. Run shared v3 canonical/signature/rejection vectors against both implementations; then independent review. Keep full v1/v2 parity, real provider/CI issuance, hosted Neon/Cloudflare behavior, device, signing, external dogfood, customer and operational gates explicitly pending.

This acceptance authorizes continued development of dependent hosted slices. It does not qualify production identity, release execution, the entire W11/W16 package or GA.

## Adversarial acceptance matrix

| Boundary | Required executable case and observable result in the first slice |
| --- | --- |
| Signature and token purpose | Valid RFC 9068 AT succeeds; tamper, `none`, wrong algorithm/key type, unknown issuer/client/audience, ID-token/workload-token substitution, missing required claim, malformed JSON, duplicate escaped claim, unsupported critical header fail with no DB/domain write. |
| Time and revocation | At-expiry boundary, future iat/nbf beyond skew, excessive lifetime, disabled principal/profile, revoked credential and invalid-before cutoff deny. Freshly refreshed token for the same eligible principal can retry its idempotent command. Expired/revoked token cannot obtain cached results. |
| Identity linkage | Same subject at a different issuer/client does not become the same principal. Same email never links principals or grants membership. Unknown active-looking claims cannot bootstrap a user or role. Human/service class confusion denies. |
| Membership and role ceiling | Exercise each of the six roles for artifact read/upload/audit and unsupported release endpoints. Forged org/project/owner/groups headers or signed token claims cannot grant access. Inactive/invited/expired membership denies. Billing-only member cannot read artifact/audit. |
| Tenant and environment | Valid member of A cannot route/read/write B, even with an A body, B body, reused artifact digest or changed JSON scope. Manifest app/environment differs from granted/derived target: deny with no write. Nonexistent and nonvisible tenant cases have the same public status. |
| DB scope/role | Direct SQL as runtime with missing/wrong tenant/principal/action context sees no private rows and cannot write out of scope or forge publication. Setting only `mixer.role=publisher` cannot grant rights. Elevated/owner/bypass/usable role-chain runtime credentials fail startup. Authz tables cannot be edited by release runtime. |
| Pool and transaction | Force connection reuse across tenants and failed/rolled-back requests; settings and context never leak. Callback on a foreign connection, after transaction closure, for another action/target, or spawned task is rejected by repository API/integration checks. |
| Revocation ordering | Hold an admitted authorization transaction, issue a real concurrent revoke, verify revoke waits; after revoke commit, a new request fails. Reverse order: authorization waits/reads revoked state and fails. Lock timeout/deadlock produces rollback/unavailable, not allow. Include project-grant insert/removal races under authz head. |
| Audit actor | Forged actor/reason/forwarded IP cannot change principal/actor; source identity/role rename after success cannot rewrite audit. Rollback creates no successful domain event; same retry produces one original event. Sensitive tokens/claims absent from DB job args/logs/responses. |
| Idempotency | Same actor/key/bytes returns same result with one audit event; changed body/action/target or different principal returns conflict without original body. Retry after membership removal denies before response lookup. Crash/uncertain commit recovers without duplicate write or audit. |
| Keys and network | Valid overlapping rotation, removed key, unknown-kid storm, response too large, too many/duplicate keys, malformed JWKS, TLS/hostname failure, redirect, private-IP/rebinding, timeout and cache expiry cases obey bounds. Required fetch outage gives 503; fresh valid known-key cache can continue. No token-selected fetch URL or unbounded cache growth. |
| Authorization outage | DB unavailable or too many matching grants yields 503 with no stale policy acceptance. Reconnect does not replay a command without fresh identity/policy checks. Secrets/provider bodies never appear in errors. |
| Public delivery separation | Existing Go tests remain green. Hosted public read regression must serve published signed data with no bearer and reject unpublished/private data; identity-provider outage does not create admin access or stop prepublished delivery. An unimplemented hosted delivery path remains pending rather than returning dummy success. |
| Protocol parity | Actual canonical v3 signature bytes, immutable conflict, mismatched scope/runtime/version and malformed/oversized requests match the preserved contract. Declare every deliberately unsupported version/endpoint; no green result from skipping the input. |

Subsequent service/CI, environment-release and approval slices must add: provider-issued workload tuple validation; service grants never obtaining human admin rights; two-person same-principal/session attacks; changed artifact/cohort/policy approval reuse; wrong destination promotion; dispatch after revoke; stale lease/fence; duplicated external effects; private delivery/cache isolation and all selected-provider outage cases. They cannot be inferred from the first slice.

## Decisions still requiring evidence

- Root freeze: approve/adjust the baseline role ceiling and per-environment grant model. These are proposed product defaults; §17 supplied role names and requirements rather than a permission table.
- Identity owner: select the provider/SSO topology, exact API/token/CI profiles, maintained Elixir libraries and versions, stable subject linkage, MFA/assurance semantics, credential-family revocation support and key rotation process. No provider support is assumed from OIDC branding alone.
- Security reviewer: accept the trusted-API/RLS threat boundary and narrowly privileged identity/policy resolver, review all role chains/function owners and verify the actual database grant topology. If the API process is assumed hostile, freeze a stronger identity-to-database mechanism before implementation claims.
- Hosted storage owner: decide normalized resource columns, versioned actor encoding, membership migration and owner/bootstrap workflows, direct Neon connection budgets, production clock monitoring and timeout settings. Existing Go schema migration behavior stays intact.
- Operations owner: qualify real provider availability/revocation, incident disable, production token lifetimes/rotation, authenticated ingress/source IP and operational audits. Test-mode success is not a provider deployment receipt.

No production deployment/publication, customer messaging, credential change, native runtime activity or schema migration was performed for this contract. See [receipt.json](../verification/hosted-identity-contract/receipt.json) for executed host checks and limitations.
