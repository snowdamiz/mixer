# Hosted transaction context PREIMPLEMENTATION preflight

The selected development seam uses a fixed Repo, the owning BEAM process, the public dynamic-Repo accessor, a fresh invocation reference, and the actual PostgreSQL backend/full transaction ID. The [final disposable run](../verification/hosted-transaction-context-preflight/run-3/receipt.json) passed 24 executable cases with zero skipped or excluded cases. Protected transaction admission must use **`queue: false`**: the pinned DBConnection implementation does not bound queued checkout waiting with the supplied transaction timeout/deadline. This is producer seam evidence awaiting root review, not membership authorization, a migration, a hosted-provider qualification or a GA acceptance.

This extends the transaction-context implementation freeze requested by the [membership and private storage contract](hosted-membership-storage-contract.md). Only the probe and this document were written. Live hosted source, dependency declarations/lock, trackers, migrations, repository/HTTP APIs and commits were outside this lane. No Patch/Skip implementation, source, fixtures or dependencies were used.

## Selected public seam

The executable specimen is [context.ex](../verification/hosted-transaction-context-preflight/probe/lib/context.ex). Its modules and arbitrary SQL helper exist only in an isolated disposable probe; they are not a proposed public product repository API.

1. Fix the Repo module internally. On entry require its configured default dynamic Repo, no active invocation marker, and public `Repo.in_transaction?() == false`. Do not accept a Repo/connection from a caller. Start one `Repo.transaction` with `queue: false`, an absolute `System.monotonic_time(:millisecond)` deadline, and timeout equal to the remaining budget, capped at five seconds. A busy pool fails before callback entry; future HTTP handling must map this to storage unavailable. A later attempt starts a fresh transaction and redoes verification/current authorization; it cannot retry by reusing a context.
2. Make `SET TRANSACTION ISOLATION LEVEL READ COMMITTED` the first SQL statement after BEGIN. Create a fresh reference and 32 random bytes encoded as a transaction-local nonce, install an owned invocation marker for callback duration, and use parameterized transaction-local settings. Set `lock_timeout` to 250 ms. Before each protected operation recalculate and set the decreasing `statement_timeout`, also passing the fixed absolute deadline and remaining timeout to the SQL call.
3. Capture `self()`, the fixed Repo module, `Repo.get_dynamic_repo()`, the fresh invocation reference, exact action/target, deadline and the actual SQL result of `SELECT pg_backend_pid(), pg_current_xact_id()::text, current_database(), current_user, current_setting('mixer_preflight.invocation_nonce', true)`. Preserve the full transaction ID as text, avoiding a 32-bit xid or a JavaScript number. `pg_current_xact_id()` assigns an xid even for this read-only identity query. The observed PostgreSQL 17 primary supports it; no read-replica or other-version fallback is qualified. PostgreSQL documents the backend identifier and full transaction ID functions in [system information functions](https://www.postgresql.org/docs/17/functions-info.html).
4. Before every repository operation reject malformed/closed contexts, a different process, fixed Repo or current dynamic Repo, a missing/mismatched active reference, nontransaction state, wrong operation/target and elapsed budget. Query the actual backend/full xid/database/current role/nonce again on the current Repo connection and require exact equality. Recheck budget immediately before effect persistence and before callback completion. The future authorization owner must additionally recheck fresh token/policy time and the actual operation/target; those are not implemented by this specimen.
5. Delete the owned marker in `after`, including explicit rollback and exceptions. The nonce and SQL budgets use transaction-local settings and disappear after commit/rollback. PostgreSQL may retain the custom setting name with an empty value; both NULL and empty are absent context, never authority. A captured returned struct is deliberately tested and remains unusable.

No private Ecto/DBConnection process-dictionary transaction keys, ETS holder identities or internal connection struct fields are read by the seam. Public `in_transaction?` alone is insufficient: direct SQL COMMIT/BEGIN left it true while xid changed from `810` to `811`. The full xid check rejected the next protected operation even after restoring the old nonce. This detects later context use; it cannot undo a raw COMMIT already executed by trusted code. Product callbacks must not expose arbitrary SQL, nested authorization, network/signer operations, async work or customer code. The fixture tasks and raw SQL in these adversarial tests are test machinery only.

The reference/nonce/context is API discipline within trusted BEAM code. Malicious code in the owning process can inspect and alter data and issue raw SQL; this is not an unforgeable authorization object or in-process compromise defense. Capturing database/current role also does not establish that the role has safe privileges. Runtime startup role/privilege/RLS admission still needs its separate implementation and evidence.

## Deadline source finding and retained failure

The passing run freezes installed, archive-verified primary-source excerpts in [primary-source-evidence.json](../verification/hosted-transaction-context-preflight/run-3/primary-source-evidence.json). Ecto SQL 3.14.0 `checkout_or_transaction` forwards options to DBConnection. DBConnection 2.10.2 `Holder.abs_timeout` chooses the earlier of `now + finite timeout` and the absolute deadline; `start_deadline` starts an absolute Erlang monotonic timer. The pool checks the exact timer reference, invalidates the checked-out holder and invokes disconnect. Postgrex 0.22.4 cancellation/disconnect closes the socket. Later writes on that holder fail, and transaction completion still requires commit.

However, `Holder.checkout_call/5` has a receive with **no timeout branch**. It starts the deadline timer only after receiving the ETS holder. [Run 2](../verification/hosted-transaction-context-preflight/run-2/receipt.json) retained the failed assumption that `deadline: now + 180` and `timeout: remaining` would also bound a queued wait. The callback did not get a slot until the holder fixture's four-second safety limit expired; that fixture exception failed the test. This run was 23/24, not a pass. Its source snapshot, exact commands/output, test summary and PostgreSQL log remain unchanged. No claim of a 180 ms checkout bound follows from it.

The correction uses the public `queue: false` option. In run 3, a busy one-slot pool rejected admission in measured **0 ms**, with the authorization specimen callback never started. Once the holder released its slot, a fresh admission succeeded. The 0 ms value is this local measurement, not a latency SLA. The final specimen does not depend on DBConnection's adaptive queue controls to enforce admission time.

Expiry does not terminate a BEAM callback. The callback's deliberate 330 ms sleep completed after its 180 ms connection deadline; the subsequent application guard rejected it, and the connection had disconnected. Changing a copied context deadline to a later value did not extend the original checkout deadline. This establishes the tested database budget behavior, not a hard callback wall-time bound or real-time scheduling guarantee. A transport/deadline failure racing an already-sent COMMIT remains commit uncertainty; the future repository must report storage unavailable and use a fresh authorized idempotent retry. This probe does not prove a commit cannot finish just after the deadline or token expiry.

## Observed executable matrix

All cases below use real Ecto/Postgrex transactions, a disposable PostgreSQL database and two fixed one-slot Repo pools. SQL Sandbox was not used. The final [test summary and observations](../verification/hosted-transaction-context-preflight/run-3/tests.json) and [complete command/output log](../verification/hosted-transaction-context-preflight/run-3/commands.json) are the evidence.

| Cases | Observed assertion |
| --- | --- |
| 01 | SQL identity stayed stable; statement budget decreased from 4998 to 4961 ms; READ COMMITTED and 250 ms lock timeout were active. |
| 02–05 | A new transaction reused backend `85203` but changed full xid `749` → `750`; post-commit/post-rollback contexts failed; spoofed old marker plus nonce in a fresh transaction still failed the xid check. |
| 06–10 | Another process, changed fixed/dynamic Repo, nested seam entry, existing transaction entry, malformed/closed context, wrong operation/target and altered backend/xid/database/role all failed closed. |
| 11–14 | Changed nonce was rejected. Commit, rollback and exception removed the SQL nonce/budgets and process marker; exception effects rolled back. |
| 15 | A callback wait crossing the application deadline rejected a subsequent write; zero earlier synthetic effect rows committed. |
| 16–17 | With no specimen deadline guard, the real absolute DBConnection deadline disconnected while the callback slept. A subsequent raw write raised ConnectionError; a late callback return without another query returned `{:error, :rollback}`. The earlier inserted row did not commit in either case; the disconnected backend disappeared. |
| 18 | Slow SQL exceeded its remaining statement/connection budget and retained zero synthetic effects. Cancellation and connection expiry race: retained runs observed both PostgreSQL `57014` and client ConnectionError. Neither error is a success or a reusable context. |
| 19 | A blocked row update raised SQLSTATE `55P03` after measured 251 ms; its prior synthetic insert rolled back. |
| 20 | Initial membership read saw active=true. After a 101 ms lock wait, a separate READ COMMITTED statement saw the concurrently committed active=false. |
| 21–22 | Direct COMMIT/BEGIN changed actual xid despite Ecto's transaction flag; the stale context failed. An unrelated raw transaction had no invocation nonce. |
| 23–24 | A changed context copy could not extend the original connection deadline. Busy pool admission failed immediately with no callback; fresh admission succeeded after slot release. |

The separate post-lock query is required because READ COMMITTED gives successive statements fresh committed snapshots. Lock acquisition and policy evaluation cannot be collapsed into a claim that a statement's earlier snapshot became fresh after waiting; see [PostgreSQL transaction isolation](https://www.postgresql.org/docs/17/transaction-iso.html). This test uses a synthetic membership boolean and gate row, not the proposed resolver, canonical lock chain, policy registry or authorization decision.

## Reproduction, provenance and limits

From the repository root run `python3 verification/hosted-transaction-context-preflight/run.py`. Each run gets a new `run-N/` directory and a short owned `/private/tmp/mxtc-*` scratch root. The driver verifies the seven installed general-purpose dependency source trees byte-for-byte against Hex package archives whose inner/outer hashes match the accepted baseline lock at `bc45a20298533b70808607b8228473b1d1efa81d`. Only verified archive members are copied into scratch. The scratch project contains only the probe; isolated `MIX_DEPS_PATH` and `MIX_BUILD_PATH` prevent live product/dependency builds. The additional live dependency work is not included. The accepted lock, package/file checksums, immutable input copies, actual observed repository HEAD, contract input hash, command arguments, selected environment overrides and full output are retained per run. Run 1 predates the explicit environment-override field; its archived driver and scratch path retain that configuration. Runs 2–3 record the overrides directly.

Observed toolchain: Python 3.14.8; Elixir/Mix 1.20.4; Erlang/OTP 29, ERTS 17.1; PostgreSQL/pg_ctl/psql 17.11 Homebrew. Runtime dependency versions are Ecto 3.14.2, Ecto SQL 3.14.0, Postgrex 0.22.4, DBConnection 2.10.2, Decimal 3.2.0, Telemetry 1.4.2 and Jason 1.4.5. No dependencies were added. An upstream dependency Mix `xref` deprecation warning remains in the complete output; no owned source warning remains in run 3.

Run 1 passed its original 22 cases. Run 2 retained the queue-bound failure. Run 3 passed the corrected 24 cases with no exclusions. Every owned cluster was stopped and every scratch build/source/socket/data directory was removed, including the failed run. No existing database was touched, no TCP listener was opened, and no native/UI process was started. The database bootstrap role was an isolated test superuser: this is transaction-seam evidence, not runtime least-privilege/RLS evidence.
