# Swift bridge native-exit CI investigation and repair

The hosted run at `26943ac` failed its experimental bridge TSan pass: the public-owner/native-exit test timed out after 22.179 seconds, and TSan reported two races. `hosted-original/` retains the complete original Swift job, jobs metadata and previous green jobs metadata. The bridge, capability adapter, guest sources and CI workflow are identical between the previous green `7855754` and `26943ac`.

The failed test used a 50 ms HTTP request and waited for a real URLSession invalidation before closing the public owner. The transport correctly completes pre-session expiry without creating URLSession, invalidation callback or native lease. A deterministic frozen original-test variant using its existing internal clock seam prints `gate=false active=0 exits=0`, reaches guest completion, and then fails the original invalidation predicate at `StorageTests.swift:11`. This establishes a flawed test precondition. The hosted log lacks predicate state, so it does not establish which exact expiry/observation route caused that timeout. The original gate can also escape after five seconds, which a delayed observer can miss.

`HTTPTests.swift` now observes actual URLProtocol start, one real transport lease and one retained native exit before close/drop triggers invalidation. Its 30-second request budget prevents the request deadline from being the test trigger. The invalidation gate still has the same five-second escape and the polling helper still uses 800 five-millisecond sleeps. The test still proves the public owner dies while native exit is retained, fifteen other constructions exhaust the sixteen-owner budget, and capacity returns only after actual invalidation. New assertions reject a gate that escaped by timeout.

The two separate hosted TSan reports are a public session's `owner` initialization on the construction queue versus `startupGuestUIV1` on a resumed task, and dispatch-source initialization in `NativeExitOwner.start()` versus `signal()` on that task. The production change in `Session.swift` explicitly publishes the fully initialized session through a lock that exists before queue scheduling. Successful construction stores under that lock, resumes a void continuation, and the resumed task takes and clears the slot under the same lock. Error/cancellation branches never fill the slot; their cleanup, one continuation resolution and constructor-tail location remain unchanged. No suppression or changed native-source lifetime is used.

Frozen candidate checks pass all 48 bridge tests in Debug, Release and TSan. Additional verification-only TSan probes pass 64 real source/timer/native-exit/drain cycles and prove all sixteen construction permits return, plus 32 actual GuestUI startup/timer/deinit/retirement cycles. The GuestUI probe drops the only public owner and checks weak deallocation, exactly one retirement and the original constructor tail. The first extra generic probe incorrectly expected an exit to remain retained after policy-denied work was already acknowledged; `candidate-stress/` retains this failed diagnostic and it is excluded from qualification. The corrected `candidate-stress-v2/` holds actual installed-host invocation while observing the source, timer and retained exit.

Unmodified baseline filtered, full 48-test and corrected stress runs also pass locally. Local Swift 6.3.3/Xcode 26.6 differs from hosted Swift 6.2.4/Xcode 26.3, so these checks do not reproduce or close the hosted race reports. A clean replay on the pinned hosted toolchain remains pending.
