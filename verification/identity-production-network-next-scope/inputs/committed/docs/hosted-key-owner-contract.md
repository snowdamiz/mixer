# Hosted profile, key ownership and HTTPS cache contract

Status: **candidate for root freeze; no owner, cache or configured adapter is implemented**. This specifies the next bounded W11/W16 slice under product-plan §§13, 17 and 18. It preserves the [identity contract](hosted-identity-contract.md) and the pure verifier accepted at `f18ea41910bc06a95d04cc19081a73dc31b5a96e`. Root must freeze the proposed seams and transport selection before dependent code/dependency changes. This document does not accept a GA gate or select an identity provider.

## Frozen verifier boundary

Keep `TrustSnapshot.new(profile, raw_jwks_json, fetched_at, fresh_until)` and `AccessTokenVerifier.verify(compact_token, now, snapshot)` unchanged. The profile has exactly `profile_id`, `profile_version`, `issuer`, `audience`, `client_id`, `identity_class`, `enabled`; network/cache fields belong in an **outer configured entry**, never in this map. Preserve RS256, all existing JSON/JWK/token limits, 900-second human/300-second service lifetimes, 30-second future allowance, exclusive expiry/freshness, and the exact `VerifiedIdentity` fields described in [the verifier contract](hosted-token-verifier.md).

`Verifier.authenticate/2` still returns only `{:ok, VerifiedIdentity.t()}` or `{:error, :unauthenticated | :identity_unavailable}`. It does not expose refresh reasons or add a third error. Future HTTP admission may independently return `429 rate_limit`; an exhausted internal owner/fetch/waiter budget maps to `:identity_unavailable`. No authenticated route, membership permission, database authority or fallback credential is supplied by this slice.

## Proposed ownership and seams

One supervised `MixerHosted.Identity.KeyOwner` owns the current immutable manifest, snapshots, monotonic deadlines, cooldowns, unknown-key entries and fetch registrations. Its data is private; arbitrary request code cannot install a snapshot. A separate bounded worker supervisor owns transport processes. BEAM module/type privacy is application discipline, not protection against hostile code already executing inside the trusted process.

| Seam | Required behavior |
| --- | --- |
| `ConfiguredVerifier.authenticate(token, now)` | Implements the frozen behavior for one **root-configured profile binding**. The first adapter has one explicit binding; it does not guess a default from a token. Up to eight reviewed bindings can later use the same owner. Token issuer/client/kid never constructs a profile or URL. |
| `KeyOwner.checkout(profile_id)` | Returns a private lease containing manifest generation, profile version, snapshot generation and deadlines, or authoritative disabled/removed/unavailable state. No raw token is sent to the owner. |
| `KeyOwner.finish(lease)` | Serializes the final fence after pure verification: current enabled binding, exact profile/version/snapshot generation, valid clock and both freshness bounds must still match. A stale checkout alone can never produce a successful adapter result. |
| `KeyOwner.replace_manifest(expected_generation, candidate)` | Trusted configuration path only. Validate the complete manifest and compare the expected generation; publish all current pointers in one serialized transition or publish nothing. An older/same conflicting revision cannot overwrite a current revision. This is not a customer API. |
| `JWKSTransport.fetch(entry, deadline_mono)` | Returns a complete bounded authenticated response candidate plus timing/cache metadata, or a bounded internal failure category. It cannot install trust or accept token input. No retries, redirects, pooling or HTTP cache are hidden in the transport. |

These are proposed **internal** seams, not additions to the accepted pure API. The adapter runs the cryptographic helper in its already-admitted request process, not inside the owner's serialized callback. On a failed final fence, disabled/removed means `:unauthenticated`; another current revision/snapshot can be checked once from a new checkout. A second race or unavailable current trust returns `:identity_unavailable`. Never return an identity built under the retired version. An operation admitted before a disable may finish before that serialized transition; a successful result fenced after it must deny.

An outer entry is `%{profile: exact_profile, jwks_endpoint: %{host: dns_name, port: 443, path: exact_path}, transport: :hosted_https}`. Require an explicit reviewed issuer-to-endpoint association; the endpoint need not share the issuer's host. Use no discovery, token-selected URL, bearer-dependent header or mutable application-environment authority. The entry is copied/validated at installation, and cannot be changed through a caller retaining its original value. Host is canonical lower-case ASCII DNS, without trailing dot, IP literal, userinfo or wildcard; path is an absolute ASCII path with unreserved characters and `/`, no percent encoding, dot segments, query or fragment. A non-443 port requires its own explicit reviewed production entry; test ephemeral ports use the isolated test transport only.

At most **eight total configured profiles**, enabled or disabled, are retained. Issuer/client/class are immutable for a profile ID; changing them requires a newly provisioned ID and identity binding. Audience/endpoint/trust-policy changes and re-enable use strictly increasing `profile_version` for the same ID; no in-place reinterpretation. Emergency disable may retain the current version while incrementing manifest generation (and, in the future DB seam, authorization revision). New enabled versions atomically replace old authority and start unavailable until their own valid candidate is installed. A separately staged validated replacement may avoid that gap only if its exact profile/version/endpoint still matches at commit. Disable/removal takes effect immediately without waiting for a fetch. Cancel old work; late results cannot publish through a generation mismatch. Successful key refresh atomically replaces the entire set, including key removals, even if the previous set was still fresh. An invalid candidate retains only the previous snapshot's original deadlines. Removed profiles retain only a bounded 30-second attempt tombstone; cap live profiles plus tombstones at 16 and reject configuration churn exceeding that bound. This preserves per-profile cooldown across remove/re-add without unbounded history.

Current revision here means **this process's reviewed configuration generation**. The coordinated future storage seam is `mixer_authz.identity_trust_profiles(profile_id, current_version, enabled, issuer, client_id, identity_class, revision)`: it contains no JWKS, TLS, endpoint or private-key fields. Authorization locks that profile row `FOR SHARE` before principal/family/organization-head/project-head locks, and matches the verified profile/version and exact issuer/client/class. Version/disable updates acquire the exclusive profile lock and increment the authorization revision. A DB-only emergency disable may leave local cryptographic verification successful while its snapshot is fresh; the authoritative transaction **must still deny** because the locked row is disabled. A later activation workflow stages/validates local trust, commits the authoritative DB version/disable, then publishes the matching local generation; any propagation gap or mismatch fails closed, with no old-version fallback. It cannot atomically commit a database transaction and an in-memory pointer. This owner slice implements neither database access nor that future workflow. Deployment propagation, cross-node disable ordering, principal/credential state, current membership and target/action policy remain a separate authorization slice; no allow cache is introduced for them.

## TLS, DNS and HTTP transport decision

Recommend exact **Mint 1.11.0**, Apache-2.0, subject to root selection and later implementation review. Retain the existing locked HPAX **1.1.0** (Apache-2.0) satisfying Mint's required `~> 1.1`; HTTP/2 is disabled. Omit optional CAStore and explicitly pass the deployment's loaded OTP CA roots. Root must add Mint's exact pin/checksum, license and purpose to `hosted/mix.*`/`THIRD_PARTY.yml` in its owned dependency slice; this contract changes neither. [Hex release metadata](https://hex.pm/api/packages/mint/releases/1.11.0) and the [publisher source/tag](https://github.com/elixir-mint/mint/tree/v1.11.0) support this selection.

The observed runtime is OTP **29.1.1**, ERTS **17.1**, inets **9.8**, ssl **11.7.7**, Elixir **1.20.4**. Online OTP docs currently describe a later patch; the installed source hashes/API excerpts and executed probe are the local authority. OTP `:ssl` itself supports a pinned address with a distinct SNI/hostname reference and ordinary chain validation. The installed `:httpc` cannot safely supply this complete fetch policy: its stream mode covers only 200/206, and `max_body_size` is bypassed by a close-delimited non-200 body. The isolated TLS probe requested a 262,144-byte maximum and received a **393,216-byte 500 body**. A post-return length check is too late to bound that accumulation. Cancellation is also asynchronous. See [OTP httpc options](https://www.erlang.org/doc/apps/inets/httpc.html#request/5), [OTP TLS reference-name checks](https://www.erlang.org/doc/apps/ssl/ssl.html#connect/4) and [the local receipt](../verification/hosted-key-owner-contract/receipt.json).

Mint provides an IP-address argument separate from the hostname, status/header/data events for every status, a bounded HTTP/1 parser and caller-owned socket lifecycle. Use its public API as follows, with all values constructed from the frozen entry and accepted DNS answer:

```elixir
Mint.HTTP.connect(:https, accepted_ip_tuple, entry.jwks_endpoint.port,
  hostname: entry.jwks_endpoint.host,
  protocols: [:http1], mode: :passive, max_header_list_size: 10_240,
  transport_opts: [verify: :verify_peer, cacerts: configured_ca_roots,
    timeout: remaining_ms, send_timeout: remaining_ms, send_timeout_close: true,
    versions: [:"tlsv1.2", :"tlsv1.3"], recbuf: 16_384, buffer: 16_384])
# request/5: GET, exact configured path, fixed headers, nil body
# Require :ssl.peername(Mint.HTTP.get_socket(conn)) == {:ok, {accepted_ip_tuple, port}}
# recv/3: timeout is remaining total budget, not a renewed two seconds
# close/1: success, rejection, timeout, cancellation and shutdown
```

Do not override verification callbacks, disable SNI, use `verify_none`, enable a proxy, downgrade TLS or enable HTTP/2/address-family fallback. Set one address family matching the accepted tuple, and make one connection attempt. Mint does not implement the owner's retry/cache policy. Its `recv/3` timeout **leaves the socket open**; `after` cleanup and a supervisor watchdog must close/kill it. No connection is reused after any result. There is no cross-origin TLS session/connection reuse.

1. Resolve only the configured DNS name, A and AAAA, under the same two-second absolute deadline. Use OTP `:inet_res.resolve/5` with explicit remaining timeout and the deployment's trusted recursive resolvers; inspect raw answers with `:inet_dns` and enforce eight CNAME hops, 16 distinct terminal addresses total and a 64 KiB DNS-message ceiling. Use one resolver call/socket at a time per worker and a bounded resolver retry setting; never reset the total deadline. Do not use the system resolver's implicit search expansion, uncontrolled CNAME following or a second hostname lookup in the HTTP connection. Resolver calls/socket cleanup and hostile DNS replies remain unproved implementation tests. [OTP resolver API and deployment caveat](https://www.erlang.org/doc/apps/kernel/inet_res.html#resolve/5).
2. Reject the entire result on a forbidden address or ambiguous/overflowed answer. Normalize IPv4-mapped IPv6. Deny private, loopback, link-local, unspecified, multicast, broadcast, documentation, reserved/non-global and transition/tunneling ranges, including cloud metadata addresses and IPv6 ULA. Freeze the address classifier against the reviewed [IANA IPv4](https://www.iana.org/assignments/iana-ipv4-special-registry/iana-ipv4-special-registry.xhtml) and [IPv6](https://www.iana.org/assignments/iana-ipv6-special-registry/iana-ipv6-special-registry.xhtml) special-purpose registries; an unclassified address fails closed. Pin one deterministic accepted tuple, verify the actual TLS socket peer equals that tuple/port before sending HTTP, and never re-resolve or follow an alternate hostname. A later DNS answer cannot change this socket's destination. Hosted egress controls provide an additional boundary; DNS filtering alone does not attest the network route.
3. Require ordinary CA-chain, validity and hostname checks against the configured host, with SNI and `Host` for that same host/port. Load nonempty configured CA roots before admission; missing roots make identity unavailable. No client certificate, bearer, cookie, proxy authorization, forwarded authorization or user-selected header is sent.
4. Send only `GET` for the exact path, `Accept: application/jwk-set+json, application/json`, `Accept-Encoding: identity`, `Connection: close`, plus the generated Host header. Accept final **200 only**. Reject 3xx without following Location, 304 without reuse, 206, upgrades and all other final statuses immediately. The first slice performs unconditional fetches; no ETag/Last-Modified state or 304 revalidation exists. Bound informational responses to four; each status/header/trailer section is capped at 10 KiB by Mint, and the wrapper additionally caps retained header metadata at 10 KiB/64 fields for the whole exchange. Reject nonempty trailers and response-directed cache/security metadata in them.
5. Require `application/jwk-set+json` or `application/json` (optional UTF-8 charset), absent/identity Content-Encoding and absent/exact chunked Transfer-Encoding. Reject unsupported encodings, contradictory framing, duplicate/conflicting singleton metadata or invalid lengths. Reject declared Content-Length over **262,144** before retaining a body. Count data events with overflow-safe arithmetic and reject before appending an event that crosses **262,144 actual body bytes**. Require complete framing; partial/truncated/error results never become candidates. Only complete JSON goes to the unchanged `TrustSnapshot.new/4`, which validates all 1–16 keys atomically.

The body limit is an **accepted/retained payload limit**, not an assertion that TLS buffers or process RSS equal 256 KiB. In the fixture, passive `recv(conn, 0, ...)` sometimes batched more than one TLS record (one retained failed harness assumption observed 294,874 bytes at the crossing; final run observed 278,490). Socket `recbuf`/`buffer` are not a maximum response/body or RSS limit. The full integration slice must measure hostile fast/slow streams, parser buffers, mailbox/heap growth and socket release with four workers. If its declared process-memory budget cannot be demonstrated, do not accept the transport implementation; change bounded read/admission strategy and re-review. This feasibility probe does not establish that remaining resource bound.

Mint 1.11.0 was the latest stable non-retired Hex release at review. Its release metadata reported no listed advisories; the publisher advisory endpoint returned 14 records, retained verbatim in [mint-advisories.json](../verification/hosted-key-owner-contract/mint-advisories.json). Source/changelog contains the 1.11 fixes for HTTP/1 Transfer-Encoding order and HTTP/2 frame/decoded-header limits (CVE-2026-94194, CVE-2026-92103, CVE-2026-91043), plus earlier line/header/chunk limits. One older advisory's broad affected range overlaps its stated patched range; retain that source inconsistency rather than calling the package universally vulnerability-free. Pinning, HTTP/1 only, strict framing, no pooled reuse and bounded wrapper tests are all required. Refresh publisher/Hex advisories when root selects the dependency and on later dependency updates. [Publisher security advisories](https://github.com/elixir-mint/mint/security/advisories).

## HTTP freshness and clocks

Use a deliberately narrow RFC 9111 policy, qualified with the selected provider. Require one valid Date, at most one valid Age (default zero), and either valid Cache-Control `max-age` or valid Expires relative to Date. An additional `s-maxage` or Expires lifetime can shorten the result, never lengthen it. No heuristic/default freshness. Reject malformed/ambiguous repeated freshness directives, `no-store`, `no-cache`, `max-age=0`, `Vary: *`, unsupported nonempty Vary, or a Date more than 30 seconds in the future. `stale-if-error`/`stale-while-revalidate` never authorize stale-key use. Unknown well-formed directives grant nothing. Missing/unusable freshness makes a fetch unusable for this cache; the first slice has no zero-TTL one-request exception.

At HTTP request send and complete response receipt capture paired wall/monotonic times. Compute RFC 9111 §4.2.3 conservatively:

```
apparent_age = max(0, response_wall - Date)
response_delay = response_mono - request_mono
corrected_initial_age = max(apparent_age, Age + response_delay)
remaining = floor(min(300, declared_http_lifetime - corrected_initial_age))
fetched_at = floor(response_wall_unix_seconds)
fresh_until = fetched_at + remaining
```

Subtract elapsed monotonic parse/validation/publication time before installation. Require at least one remaining whole second; never round up. Retain both the original monotonic expiry and the exclusive Unix `fresh_until`. A snapshot is usable only while **both** bounds hold and `fetched_at <= now < fresh_until`; `fresh_until - fetched_at <= 300`. Do not reset clocks when copying/reading a snapshot, entering a cooldown, restarting a request, failing a fetch or accepting a late result. [RFC 9111 freshness/age](https://www.rfc-editor.org/rfc/rfc9111.html#section-4.2.3).

Use Unix seconds only for token/snapshot dates and HTTP Date, and monotonic milliseconds for deadlines, cooldowns and eviction expiry. `now` is the trusted application clock sample supplied to the frozen behavior, never an HTTP parameter or token claim; tests inject a paired clock explicitly. Invalid numeric dates, monotonic reversal or a wall-vs-monotonic discontinuity beyond a frozen one-second tolerance makes the owner unavailable and invalidates resident trust until a stable sample and a new authenticated fetch. A backward clock change cannot extend cache life. A forward jump may expire tokens/keys early and cannot resurrect them. Deployment clock synchronization/monitoring is a later operational gate.

## Refresh, negative cache and errors

There is one flight per profile and at most **four fetch workers/process**. Each flight's absolute monotonic deadline is `admitted_at + 2,000 ms`, covering scheduler queue, DNS, connect/TLS, request send, complete response, JSON/key validation and publication. Every sub-operation receives the remaining budget. A late complete candidate is rejected. The watcher cancels/kills at expiry; slots remain occupied until socket cleanup and the worker's `DOWN` are observed, so a timed-out but still-running operation cannot open a fifth socket. Unresponsive cleanup makes that slot unavailable; it cannot silently be reused.

Record a per-profile attempt at flight admission, including failures; the next attempt is no earlier than **30,000 monotonic ms** later. No automatic HTTP transport retry, DNS-address retry, refresh-on-signature-failure or token-driven rate reset. Coalesce request/refresh triggers; do not queue duplicate flights. Keep at most eight queued profile IDs (one per configured profile), 16 admitted authenticate calls/profile and 128/process, including calls verifying or waiting; waiters have their own expiry no later than the flight deadline. Admission must reserve bounded counters before sending owner/supervisor messages, rather than relying on a GenServer's unbounded mailbox. Once full, return unavailable without spawning or appending. Root's future HTTP layer supplies independent bounded request/IP admission. Retain at most eight active validated snapshots (128 keys), four in-progress transport/validation candidates (64 additional keys), and one scheduling record/profile; request checkout values remain bounded by admitted calls.

| Observed current state | Adapter result and permitted refresh |
| --- | --- |
| Disabled/removed configured binding | `:unauthenticated`, no token verify or fetch. |
| Fresh snapshot, matching key | Pure verification; malformed token/claims/signature fails `:unauthenticated`. No network for known-key signature failure. |
| Fresh snapshot, absent valid bounded kid | **`:unauthenticated` immediately**, regardless of refresh success/outage/cooldown. Optionally trigger one eligible background flight; never wait and relabel a fresh authoritative absence as unavailable. |
| No current fresh snapshot (cold, expired, clock fault, replaced revision) | Join/start one admitted required flight within its deadline. Success verifies once against the new current snapshot; matching absence gives `:unauthenticated`. Failed/invalid/zero-freshness fetch, cooldown, full capacity or timeout gives **`:identity_unavailable`**. No stale fallback. |
| Unknown configured binding or rejected complete manifest | Never accept a caller-supplied profile. A removed existing binding denies; absent required startup binding is a configuration failure/unavailable service. |
| Owner/process unavailable | `:identity_unavailable`, no direct-verifier bypass. |

The adapter may inspect only an already byte-bounded protected header using the accepted `Encoding`/`BoundedJSON` rules and the same exact alg/typ/kid constraints, solely to distinguish an absent kid after the pure result. The extracted kid supplies no identity, URL or algorithm authority. Do not infer “unknown key” from every `:unauthenticated`, expose a weaker parser or change the pure verifier's errors.

Retain at most **128 unknown-kid entries/profile**, each a bounded kid, snapshot generation, insertion sequence and `expires_mono = min(first_seen + 30,000, snapshot_expiry)`. Hits do not extend expiry or trigger a fetch. Evict expired entries first, then the smallest insertion sequence (kid byte order breaks a tie); a hit does not reorder FIFO. A successful snapshot replacement clears the old negative cache atomically, so a newly published key is not hidden by an old miss. Failed refresh neither clears authoritative keys nor extends negative/snapshot expiry. No random bearer or unknown issuer allocates a new profile, clock, worker, metric label or negative entry. Log only enumerated failure categories and bounded configured profile IDs; no bearer/JWT, subject, kid, raw response, cookie, query secret or full certificate is logged in production.

## Startup, shutdown and remaining tests

Start configuration/clock/admission state and the owned worker supervisor before the configured adapter becomes usable. Invalid required configuration fails startup explicitly; valid empty key state keeps protected identity unavailable while liveness can stay up. Cold start obtains authenticated trust through at most four flights; do not import a stale disk key cache. Use one bounded scheduling record/profile; optional pre-expiry refresh still obeys the 30-second attempt rule. Provider freshness below 30 seconds can create intentional unavailable gaps; do not hide that incompatibility by extending trust. Container stop/wake restarts cold; deployment/fleet fetch quotas remain separate operational qualification.

Shutdown stops admissions, cancels queued work, releases waiter monitors/timers, closes each owned socket and terminates/awaits all owned workers. In-flight callbacks after shutdown/generation change are ignored. Empty cache is safer than reconstructing authority from delayed messages. Do not alter other applications' inets profiles, resolvers, processes, simulators or data.

An explicit test-only constructor may replace the resolver/CA root and admit loopback for one isolated fixture. It must not be configurable in a production release or weaken hostname/chain checks. Use only generated ephemeral test keys and clean every listener/process/key directory on both pass and failure.
